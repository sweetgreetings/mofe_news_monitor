## What this app is

A single-user, local-only desktop-style web app for a press-monitoring worker at the Ministry of Economy and Finance (재정경제부). It periodically scrapes Naver News search results for configured keywords, groups the articles into auto-generated sub-headings, and shows the results in a browser at `localhost`. Full spec: [PRD.md](PRD.md); condensed version: [prd_lite.md](prd_lite.md).

## Architecture (PRD section 8 original plan superseded — see DESIGN.md §3)

The original PRD plan (FastAPI + SQLite + APScheduler) was replaced during design with a simpler file-based approach to lower implementation difficulty. This is what's actually built:

- **No web framework**: plain Python scripts regenerate static HTML files (`index.html`, `history.html`, `home.html`) that are opened in the browser. No FastAPI, no Django.
- **Storage**: local JSON files under `data/` (`articles/`, `settings.json`, `hidden_articles.json`, `group_overrides.json`, `group_labels.json`) — no SQLite.
- **Scheduling**: a lightweight polling loop (`app/scheduler.py`, no APScheduler), checking every 10s [Changed: 2026-08-07, was 60s — 60초 간격이면 정시 슬롯을 막 지나친 tick 바로 다음 tick(최대 60초 뒤)까지 감지가 늦어져 텔레그램/이메일 자동 전송이 "정각+1분"처럼 체감됐다. 이 확인 자체는 설정 파일 읽기+시각 비교뿐이라 10초로 줄여도 비용 증가는 무시할 만하다]. Each slot is a `{start, end}` time window (default: 00:00–09:00 / 09:00–10:30 / 10:30–13:30 / 13:30–16:30 KST), user-editable from the settings screen (1–10 slots, no code change needed). `end` is the slot's identity (used for the storage filename and header, same as before); `start` is the lower bound for that slot's collection window (see Collection below). Only the single most-recently-missed slot is caught up on next tick if the app was closed during a scheduled time — using its *configured* start, not the actual catch-up time; the loop pauses during OS sleep like any other process and resumes catch-up on wake.
- **One exception to "no server"**: `app/settings_server.py` is a minimal `http.server`-only local HTTP server on `127.0.0.1:8765` that handles settings saves and article curation (hide/reorder/rename), and also serves the three static HTML screens from the same origin (needed because browsers block navigation from `http://` pages to `file://` paths).
- **External API**: Naver News Search API — credentials read from `.env` (`NAVER_CLIENT_ID`, `NAVER_CLIENT_SECRET`), never hardcoded or committed. [Added: 2026-08-03] Telegram Bot API (`app/telegram_bot.py`) is a second, optional external integration — credentials (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`) also come from `.env`, but unlike Naver's, missing/invalid Telegram credentials never stop the app from starting or running; sends are just skipped with a log warning (`is_configured()`).
- **Target OS**: Windows, single local user, no auth/login layer.
- No separate LLM/AI API is used for classification — sub-heading grouping, summaries, and keyword extraction are rule-based (word-frequency grouping over article **descriptions**, not titles — title wording varies too much by outlet to group well), explicitly to avoid API costs.

## Core business rules to preserve (PRD section 5)

These are product-defined constraints, not implementation details — get them wrong and the feature is wrong even if the code runs:

- **Collection**: [Updated: 2026-07-25] Keyword *groups*, not a flat keyword list — up to `MAX_KEYWORD_GROUPS` (6) groups, each with up to `MAX_KEYWORDS_PER_GROUP` (7) keywords and its own OR/AND mode, at least 1 group required. Between groups the relationship is always OR (any group's condition being met is enough); within a group it's that group's own OR/AND. The "기관 정보 (기본)" group is no longer fixed/read-only — it's seeded once on first load from `app/config.py` `BASE_GROUP_KEYWORDS` (재정경제부/재경부/기획재정부/기재부/정부/구윤철/이형일) via a one-time migration flag (`app/settings.py` `load_settings`, `base_group_seeded`), then behaves exactly like any other group: renamable, its keywords editable, and the whole group deletable (an admin's institution can change). [Updated: 2026-07-25] Each group also has an `include_in_scrap` flag (checkbox in the settings screen, one-time migration defaults existing groups to `True` for backward compat): the scheduled/official scrape (`app/scraper.py` `collect_run`) only searches groups with this flag on, while the real-time view (`app/live_renderer.py`, see below) always searches *all* groups regardless of the flag. At least one group must have it on (`app/settings.py` `validate_keyword_groups`). This lets an admin keep broad topic groups (e.g. 부동산, 환율) live-view-only and hand-pick individual articles into the official scrape via the "→ 스크랩" button, without those topics silently inflating every scheduled run. Editable from the settings screen (no code change needed) — `app/settings.py` `save_keyword_groups`/`validate_keyword_groups`, `app/naver_api.py` `search_articles_by_groups` (dedups identical keywords across groups so the Naver API isn't called twice for the same word). No result-count cap, only same-day (KST) articles. [Fixed: 2026-08-06] `search_articles_by_groups` used to search each unique keyword sequentially — with a live keyword set this measured at ~19s wall-clock (dominated by whichever keyword happens to have the most same-day articles, since `_search_one_keyword` paginates up to `_MAX_START`/100 = 10 pages per keyword). Switched to a bounded `ThreadPoolExecutor` (`_MAX_CONCURRENT_KEYWORD_SEARCHES = 5`) — measured ~5.3s for the same keyword set, a floor set by the single slowest keyword rather than the sum of all of them (more concurrency wouldn't help further without also parallelizing pagination *within* one keyword, which isn't done). A per-keyword `_search_safely` wrapper catches `requests.exceptions.RequestException` so one keyword's failure doesn't take down the others — this was added specifically *because* concurrency makes Naver's per-second rate limit easier to hit than sequential calls did (confirmed live during testing: a 429 on two keywords, gracefully degraded to empty results for just those two rather than crashing the whole search). 5 was chosen as a bounded middle ground for this reason, not unlimited concurrency. Note: diagnosing this, a naive test script that skipped `app.settings.active_search_groups` (which strips `disabled_keywords` before searching) wrongly made it look like a disabled keyword ("정부") was the dominant cost at 47s/1000-result-cap — the real app already excludes disabled keywords correctly via `active_search_groups`, so that specific number was never real, though the general "one broad keyword can dominate the total time" finding still holds and is what motivated this fix.

## Working rules

- 모든 설명과 주석은 한국어로 작성한다.
- 새 파일은 이 프로젝트 루트 폴더(`my_app`) 안에만 만든다.
- 코드를 바꾸면 반드시 무엇을 왜 바꿨는지 한 줄로 알려준다.
- `.env` 등 비밀 정보 파일은 `.gitignore`에 등록해 두고, 절대 커밋하지 않는다.
- 파일을 지워야 할 때는 바로 삭제하지 말고, `trash-can` 폴더를 만들어 그 안으로 옮겨만 둔다. 작업이 끝난 뒤 사용자가 직접 확인하고 삭제한다.
- 이미 설치된 서브에이전트(bkit의 gap-detector 등)를 필요할 때마다 적극 활용한다.
