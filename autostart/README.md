# 자동 실행 (macOS)

## ⚠️ 설치 위치 — 데스크탑·서류·다운로드 폴더에 두면 안 된다 [추가: 2026-09-04]

macOS는 이 세 폴더를 보호한다(TCC). **launchd가 띄운 백그라운드 프로세스는 이 폴더를
아예 못 읽고, 프롬프트도 안 뜨고 조용히 거부당한다.** 실측(2026-09-04):

```
launchd 에이전트에서 읽기 시도
  ~/press-monitor/probe.txt      → 읽힘
  ~/Desktop/my_app/main.py       → Operation not permitted
```

파일 권한(`-rw-r--r--`) 문제가 아니라 보안 정책이라 `chmod`로는 못 푼다. 실제로 이 앱은
2026-09-03 자동 실행을 붙인 뒤 **~/Desktop/my_app 에 있어서 단 한 번도 자동으로 뜬 적이
없었다** — 에이전트가 30회 넘게 죽는 동안 아무 데도 안 드러났고, `install.sh`는 "✅ 등록
완료"라고만 했다(그래서 지금은 install.sh가 실제 실행까지 확인하고, 실패하면 원인과 고치는
법을 알려준다).

**지금 위치: `~/press-monitor`** (보호 대상 아님). 데스크탑에는 같은 이름의 심볼릭 링크
`~/Desktop/my_app → ~/press-monitor`를 뒀으니, 평소 쓰던 방식은 그대로다. `app/config.py`의
`BASE_DIR`가 `Path(__file__).resolve()`라 링크로 들어와도 실제 경로 한 곳으로 모인다 —
data 폴더가 둘로 갈릴 일이 없다.

**옮길 때는 `bash autostart/install.sh`를 새 위치에서 다시 돌린다** — plist에 절대경로가
박히므로 옮기기만 하고 재설치를 안 하면 그대로 죽는다.


앱을 **로그인할 때마다 백그라운드로 띄운다.** 손으로 `python3 main.py`를 켜는 걸 잊어서
회차가 통째로 비는 걸 막는 게 전부다.

```bash
bash autostart/install.sh
```

해제는 `bash autostart/uninstall.sh`.

## 왜 필요했나 (실측)

2026-08-19~09-02, **예정 78회차 중 14회(18%)가 비었다.**

| 날짜 | 누락 | 사유 |
|---|---|---|
| 8/28(금) | 4회 (11:00·14:00·17:00·19:30) | 앱 안 켜짐 |
| 8/29(토)·8/30(일) | 6회 (전부) | 앱 안 켜짐 |
| 8/31(월) | 2회 (06:00·09:30) | 앱 안 켜짐 |
| 8/22(토)·8/23(일) | 2회 | 앱 안 켜짐 |

**놓치면 되살릴 수 없다.** 네이버 뉴스 검색 API에는 기간 지정 파라미터가 없고 키워드당
최신 1000건까지만 준다. 정기 스크랩 키워드 8개의 "1000건이 며칠 전까지 닿는가"를 실측하면
(2026-09-03):

```
재정경제부        1일 전  ← 병목
재경부            4일 전      재정경제기획위원회  4일 전
구윤철            7일 전      기획재정부          9일 전
기재부           86일 전      재경위            135일 전
```

가장 좁은 게 전체를 결정하니 **소급 한계는 하루**다. 그래서 "나중에 채우는" 기능을
만드는 길은 애초에 막혀 있고, 안 놓치는 것 말고 방법이 없다.

## 이걸로 해결되는 것 / 안 되는 것

**된다** — 로그인만 하면 앱이 떠 있다. 켜는 걸 잊을 수가 없다.
크래시하면 launchd가 30초 뒤 다시 살린다(`KeepAlive`).

**안 된다** — **컴퓨터가 잠들어 있거나 꺼져 있는 동안은 여전히 못 모은다.**
자동 실행은 "앱을 켜는" 문제만 풀지 "컴퓨터가 깨어 있는" 문제는 못 푼다.
주말 회차(토·일 10:00 / 13:00 / 16:00)를 실제로 받으려면 아래를 함께 해야 한다.

```bash
sudo pmset -c sleep 0
```

전원 어댑터가 연결돼 있는 동안 잠자기를 안 한다(화면은 그대로 꺼진다). **이 명령은
관리자 암호가 필요해서 직접 실행해야 한다.** 되돌리려면 `sudo pmset -c sleep 10`.

노트북 뚜껑을 닫으면 이 설정과 무관하게 잠들고, 컴퓨터를 아예 끄면 당연히 안 돈다.
주말에 전원을 내린다면 `sudo pmset repeat wakeorpoweron SS 09:50:00`(토·일 09:50에
자동으로 깨움)을 함께 걸어야 하는데, 이건 기종에 따라 동작이 달라 실제로 깨는지
한 번 확인이 필요하다.

## 깨어난 뒤에 무슨 일이 일어나나

**오늘 놓친 회차는 전부, 오래된 것부터 채운다**(PRD 기능1 규칙9, `app/scheduler.py`
`find_slots_to_run` — 2026-09-04에 "가장 최근 1개만"에서 넓혔다). 밤새 잠들었다 아침에
깨면 그 사이 지나간 회차가 차례로 다 수집된다. 회차 하나가 실패해도 나머지는 계속 가고,
실패한 것은 다음 확인(10초 주기) 때 자연히 다시 시도된다.

여러 회차를 한꺼번에 채워도 **자동발송은 마지막 회차에 대해서만** 일어난다 — 몇 시간
지난 회차가 뒤늦게 발송되지 않는다. 나머지는 정기 보관함에 그대로 남아 필요하면 직접
보내면 된다.

**어제 이전 회차는 못 채운다** — 위 1000건 실측대로 소급 한계가 하루이기 때문이다.

## 동작 확인

```bash
launchctl list | grep local.press-monitor
```

세 값이 `PID  0  local.press-monitor` 모양이면 정상(가운데가 마지막 종료 코드).
실행 로그는 평소대로 `data/logs/app.log`, launchd 자체의 출력은
`data/logs/launchd.out.log` / `launchd.err.log`에 쌓인다.

앱이 이미 백그라운드로 떠 있는 상태에서 `python3 main.py`를 그냥 실행하면 중복 실행
자물쇠(포트 8765)에 걸려 **두 번째 앱은 안 뜨고 브라우저만 원래 앱 화면으로 열린다** —
즉 손으로 실행하는 행동이 그대로 "화면 열기"가 된다.

## 코드를 고쳤으면 재시작해야 화면에 반영된다 [추가: 2026-09-10]

```bash
launchctl kickstart -k gui/$(id -u)/local.press-monitor
```

파이썬은 프로세스가 뜰 때 `app/*.py`를 한 번 읽어 메모리에 올린다. 화면
(`index.html`·`preview.html` …)은 회차마다 다시 구워지지만 **구워내는 코드는 앱이 뜨던
순간의 것**이라, 자동 실행을 붙인 뒤로는 파일을 고쳐도 재시작 전까지 화면이 안 바뀐다.
손으로 켜던 때는 매번 껐다 켜서 이 문제가 드러나지 않았다.

실제로 그렇게 6일을 흘려보냈다(2026-09-10 제보). 소제목 ✏️ 이름 바꾸기가 현재 이름을
미리 채우도록 9/9에 고쳤는데 화면은 계속 빈 칸으로 떴다 — 앱이 9/5 00:07부터 떠 있어서
9/9자 `app/renderer.py`를 한 번도 읽은 적이 없었기 때문이다. 그 사이 `index.html`은
회차마다 멀쩡히 다시 구워지고 있었으므로 "반영이 안 된다"는 신호가 어디에도 안 났다.

고쳤는데 화면이 그대로면 **먼저 이걸 의심한다.** 재시작 뒤에는 브라우저 탭도 한 번
새로고침한다 — 열려 있던 탭은 옛 HTML을 그대로 들고 있다.
